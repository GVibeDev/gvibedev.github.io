GVibeDev Manifesto

AI is leverage, not autopilot.

The point of better tools is not to disappear from the work. It is to attempt more ambitious work while keeping intent, judgement, testing and responsibility human.

GVibeDev is built in public as a workshop: ideas become systems, pages, games, tools and documents through iteration rather than claims.

Working ruleThe prompt is not the process.

A useful result still needs requirements, context, comparison, correction, testing and a person willing to reject what does not work.

01 · Build before you preach

Working things are stronger than declarations.

Ideas matter, but the workshop is judged by what survives contact with reality. A playable build, a usable tool, a working page or a repeatable workflow teaches more than a confident description of what should work.

Build first. Then document what the build actually taught you.

02 · Amplify judgement

AI extends capability. It does not inherit judgement.

Models can accelerate writing, coding, comparison, analysis and prototyping. That speed is useful only when somebody still decides what the work is for, what counts as correct and when an output deserves to survive.

Human direction is not a decorative final check. It is part of the architecture.
03 · Test

If it matters, make it touch reality.

Generated code must run. Interfaces must be used. Game systems must be played. Claims must be checked against evidence. A convincing output is not the same thing as a correct one.

Testing is where confidence becomes information.

04 · Failures are evidence

Keep the broken attempts useful.

A failed build, a bad generation or a wrong assumption is not wasted if it changes the next decision. Iteration works when failure is diagnosed rather than hidden.

The purpose of a development history is not to pretend the path was clean. It is to preserve what the rough path revealed.

05 · Learn while building

Capability can be acquired inside the project.

Not every project begins with every required skill already mastered. Better tools lower the barrier to entry, but they do not remove the need to understand what you are doing.

Use the project as a reason to learn the next missing piece, then make that knowledge part of the workflow.

06 · Keep decisions visible

Do not hide the human part behind the machine.

Requirements, exclusions, acceptance criteria, corrections, trade-offs and final choices are part of the work. Showing them makes AI-assisted development more understandable and more honest.

The machine may produce candidates. The project still needs an author of decisions.

07 · Prompt ≠ process

Good prompting is architecture, not incantation.

A prompt can start a task. A process maintains context, constraints, checkpoints, review and continuity across many tasks. Complex projects need the second.

This is why method matters more as the tools become stronger, not less.

08 · Access to capability

One person can now attempt work that once demanded a larger structure.

That does not make expertise obsolete. It changes who can reach the starting line. A writer can prototype tools. A designer can test systems. A small workshop can explore software, visuals, games and publishing without pretending each discipline has become trivial.

The opportunity is not effortless creation. It is wider access to serious creation.
